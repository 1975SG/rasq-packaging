# IDERM -- Architecture, compacted index

One entry per subsystem. Canonical detail lives in `docs/01_Architecture.md`, `docs/02_Core.md`, `docs/engine/*.md`, and `docs/modules/*.md` (not part of this doc set) -- this index exists for a reader who wants the shape of the whole system without reading 21 full docs. Decision rationale for the numbered items below lives in `docs/reference/Decisions_Compact.md`.

## System summary

Terminal-first, project-aware IDE. Core language: Rust (ADR-001) -- direct access to the terminal/async OSS ecosystem, memory safety for the concurrent PTY + render + filesystem-scan workload. No GUI toolkit (ADR-002): the terminal is the entire application surface (`ratatui` + `crossterm`), single static binary. Interaction model is block-mode, not stream-mode (ADR-004): tree/doctor/build panels render as IBM-3270-style protected fields with full-screen atomic redraw, not incremental per-keystroke VT100 redraw; retro CRT theming is opt-in only, never the point of the model. Mouse support is additive, never primary (ADR-005) -- every mouse action has a keyboard equivalent, so SSH/tmux use stays fully functional. The editing engine is embedded (Neovim, via `nvim --embed` + MessagePack-RPC), not authored from scratch (ADR-003) -- avoids re-implementing a buffer/undo/tree-sitter stack, a documented failure mode of prior editor projects. Neovim was chosen over Helix because Helix has no embedding API and no path to one; Helix's own plugin maintainers tried WASM three times and abandoned it for Scheme, which IDERM's own WASM plugin choice differs from in kind (doctor/repair calls are not per-keystroke-latency-sensitive the way live editing would be).

**Core's invariant**: fully functional offline, no plugins installed, on a project with one build manifest. Everything layered on top (multi-manifest, plugins, headless, AI) is additive, never a dependency of the base loop `scan -> doctor -> workspace`. Core owns the PTY passthrough, project/build detection, read-only diagnosis, confirm-gated repair, protected-field rendering, and git-state surfacing (shells out to the real `git`, never reimplements it). Core deliberately does not own: text editing (Neovim), language-specific knowledge (plugin manifests), executable custom logic (WASM plugins), or networked/AI behavior (the optional `ai` adapter).

**The core loop**: `iderm .` -> Scan -> {OK? no -> Doctor findings -> Repair dry-run diff -> confirm -> re-scan; yes -> Workspace (shell + editor + panels)}. Every later phase (plugins, headless JSON, AI) attaches to this loop without changing its shape -- plugin-extensible doctor/repair, a headlessly-queryable loop state, and an AI adapter proposing into the same confirm-gated repair step, nothing structurally new.

## Plugin ABI (ADR-007, `wit/iderm-plugin.wit`)

Hybrid split by category. Manifest data and already-standardized external tools (LSP servers, tree-sitter grammars, build tools/linters) run as native subprocesses using their own existing protocols -- no custom ABI. Executable logic (doctor rules, repair recipes, view providers) runs sandboxed as versioned WIT/WASM components, current package `iderm:plugin@0.4.0`. Semver governs interface changes (ADR-013): PATCH/MINOR additive-safe, MAJOR rejected outright at load time with a named error, never a silent misbehavior or crash. Real, still-open gap: bumping even a MINOR version breaks an already-compiled component at the `wasmtime` linker level (exact-string import matching) -- the additive-safe policy is documented and unit-tested, not yet self-enforcing at the linking layer, so every WIT bump in practice needs every plugin rebuilt regardless.

Three plugin worlds exist:
- **`doctor-rule`** -- `rule-id()` + `check(project) -> finding[]`, pure. Discovered from `.iderm/plugins/*.wasm`, merged into the same finding list the 6 built-in checks produce, ABI-gated before instantiation. A failing plugin (bad component, ABI mismatch, trap) becomes one error finding, never aborts the rest of the run.
- **`repair-recipe`** -- `recipe-id()` + `applies-to(project) -> bool` + `propose(project) -> file-change[]`, pure, discovered from `.iderm/repair-recipes/*.wasm`. v1 scope: new-file creation only, refused before reaching confirm if the target path already exists. Applied only after the same `[Y]` confirm gate built-in repair uses -- no plugin can bypass it. Path sandboxing verified against a real path-traversal attempt, refused cleanly.
- **`view-provider`** (`idermviz`, ADR-009/014/015) -- `init`/`render`/`handle-command`, returning structured `view-primitive`s (never raw ANSI). Three composable rendering techniques: box-drawing character-grid diagrams (state graphs, decision flows -- light-UML shape vocabulary, BFS-ranked layered layout), a braille sub-cell canvas (continuous measurement curves, proximity-to-limit coloring, axis ticks, a two-segment drop-line cursor), and a half-block truecolor grid (value-range heatmaps, independent per-cell fg/bg color). Six WIT primitive variants (`state-graph`, `trace`, `xy-chart`, `heatmap`, `table`, `composed`), all implemented. `composed` overlays box-drawing shapes on heatmap data via an anchored-node field, format-agnostic at the Core level (SVG/CSV convenience parsers only, no domain formats like Gerber -- that stays plugin territory). Live-refresh (`F5`) reuses `handle-command` with a reserved tick token, no ABI change. Multi-pane split view (ADR-016, up to 4 panes, fixed layout templates) and synchronized group actions across all panes (`Shift+F5/F6/F7/F10`, ADR-062/077) are both pure `App`/`ui.rs` state, invisible to a plugin. Explicit scope boundary: in scope if a primitive helps interpret/verify a number, out of scope if its purpose is to look like a real instrument display (3D field-solver visualization excluded on this basis).

Plugin permission model (`docs/engine/Permissions.md`) is capability-based, not ambient: a plugin receives `project-info` as a function argument and gets `read-file`/`list-files`/`log` host calls, all routed through one `Services` surface -- no direct filesystem handle, no process spawn, no network, no write access of any kind. Every plugin import must be explicit; nothing is granted implicitly.

## Module index

- **Doctor** -- read-only project health diagnosis, pure function of `project-info` in / `finding[]` out, no side effects. 6 built-in checks (git, build manifest, README, LICENSE presence, `compile_commands.json` validity, packaging metadata) plus merged plugin findings. Three-tier severity (`info`/`warning`/`error`), no fourth "fatal" tier -- doctor never blocks the core loop, only surfaces findings for Repair to act on.
- **Scanner** -- detects project structure on `iderm .`: build manifest(s), languages, root layout. Multi-manifest detection keeps every detected manifest side by side rather than picking one primary -- doctor reports all of them, task derivation offers a task set per manifest.
- **Build System** -- parses `compile_commands.json` to drive the build-tree panel and `run` action. Manifest *detection* is a language-plugin concern; parsing a detected manifest stays Core since the format itself is stable cross-language.
- **Repair** -- non-destructive: proposes changes as diffs, writes only on explicit `[Y]` confirm. Same confirm gate covers built-in repair, repair-recipe plugins, and `iderm ai repair`'s `--apply` flag -- no path bypasses it.
- **Git Panel** -- surfaces branch/status/diff as a protected-field panel by shelling out to the real `git`, never reimplementing git plumbing.
- **PTY / Shell Passthrough** -- the user's shell is the primary interface; IDERM surrounds it, never overrides it. Concurrent PTY I/O + terminal emulation + filesystem scanning is the stated reason ADR-001 chose Rust.
- **Rendering (block-mode UI)** -- the protected-field rendering primitive ADR-004 requires, custom-built (not available off the shelf in `ratatui`). Full-screen atomic redraw for panels; mouse click-to-expand/click-to-open is additive per ADR-005.
- **Editor Embedding** -- Neovim via `nvim --embed` + MessagePack-RPC, the same mechanism Neovim GUI frontends already use in production; no FFI boundary risk for a Rust client.
- **Idermviz** -- see Plugin ABI's `view-provider` entry above; this module doc is its full working detail.
- **Plugin ABI** -- see Plugin ABI section above.
- **Headless Interface** -- `iderm scan --format=json` / `iderm doctor --json` / `iderm graph --dot|--mermaid` / `iderm ledger record|diff|--json`, letting any external tool (editor, CI) consume project intelligence without running the TUI. Schema is versioned and locked in (`schema_version` envelope, canonicalized root path) and deliberately, permanently diverges from the plugin-facing WIT `types` shape -- two independently-versioned schemas, each fit for its own consumer, confirmed by real multi-consumer usage never needing convergence. Run Ledger is an explicit, append-only, never-a-side-effect provenance log; ledger diff does a real structural compare between the two most recent entries. A standalone CI-usable binary/crate is explicitly deferred (current binary is 37 MB / 270 transitive deps) -- `scan`/`doctor`/`ledger` already work headless on the existing binary today, this defers efficiency, not capability.
- **AI Adapter** -- `iderm ai <repair|explain|test>`, headless only, the one component that breaks the "works offline" guarantee, explicitly last in the phase sequence. Model-agnostic by construction: names an external command in `.iderm/ai.toml`, Core never talks to a network AI API directly. Reads project state via the exact same headless JSON interface any external tool uses -- no privileged internal access; if a future AI feature seems to need more, that signals the headless interface is incomplete, not a reason to special-case AI. Runs under a wall-clock deadline and an output-size cap; a project-declared "test" task is refused (not guessed) if more than one candidate matches its label.
- **Export** -- `iderm scan/doctor` JSON, dependency/build graph as DOT/Mermaid, and Figure Export (`F9`, `xy-chart` only, Core-side SVG + TikZ generation, no plugin ABI surface since Core itself is not sandboxed) all fall under this concern. PDF/compiled-report export explicitly excluded, not deferred -- a LaTeX-toolchain dependency isn't justified by any confirmed need; revisit only if one is named. IDERM exports project intelligence, never editor-buffer internals.
- **Config (`.iderm/`)** -- shareable, per-project configuration, the same role `.vscode/` plays. Explicit commit-vs-don't split: plugin/language/task/AI declarations and plugin binaries are meant to be committed (cloning the repo should reproduce the same behavior); Run Ledger and Figure Export output are per-machine/per-run state, not configuration, and should not be. Every path degrades to "absent means nothing happens," never an error. Committing a declared command (`tasks.toml`, `ai.toml`, an auto-discovered script) is exactly the shape the security trust gate exists for -- cloning alone never runs anything, first execution prompts for approval pinned to that file's content.
- **Workflow** -- the core loop diagram and which phase attaches to which point in it; see "The core loop" above.

## Engine layer

- **Data Model** -- the plugin-facing WIT `types` interface (`severity`, `project-info`, `finding`, `file-change`) is the canonical shape for the WASM plugin boundary. Deliberately distinct from the headless JSON schema, which serializes Core's own real internal structs directly -- two permanently separate consumers, not one shared schema.
- **Permissions** -- see Plugin ABI section above; not a multi-user/RBAC system, IDERM is single-user local. Capability-based enforcement, kept as a separate concern from the ABI shape itself.
- **RPC Interface** -- the external-facing interface is JSON output + JSON-RPC, not a REST/HTTP API. Consumed by external tools/CI/other editors and by the AI adapter, which uses this exact same surface with no privileged shortcut.
- **Services** -- the full host-capability surface a plugin can call across the WASM sandbox boundary: `read-file`, `list-files`, `log`. No ambient filesystem or process access; any new plugin capability must be added here explicitly, never granted implicitly -- this is what makes the sandbox meaningful rather than nominal.
- **Versioning** -- WIT package semver policy (ADR-013), enforced by a standalone unit-tested function checked at plugin load time before instantiation. Two still-open items, tracked but not blocking: Core binary versioning relative to `.iderm/` config format compatibility has no policy yet, and the Data Model itself has no independent versioning separate from the WIT package version it currently rides on.
